§3 · The frame

spec → plan → code → test → review → CI → deploy → monitor

Same loop as yesterday — bigger radius.

§3 · Spec-driven development

A spec is E1's good prompt,
industrialized

The two unloved sections do the heavy lifting:

  • Non-goals — prunes the agent's search space
  • Edge cases — each one is a test it writes and a hallucination it won't make
E9 · 40 min

Spec → plan mode → build → make it prove each acceptance criterion. Fast finishers: spec your homework feature.

§3 · Iterative dev + tests

Two house rules

1. Tests are the spec — and they're read-only
2. The agent runs the tests itself after every change

With a feedback loop it's an engineer.
Without one it's a very confident typist.

E10 · 30 min

cd day2_adlc/tdd_kata && node --test — starts red. Round 2: new requirement, tests first, you approve them.

§3 · CI/CD

Agents propose.
Pipelines dispose.

cat failure.log | claude -p "triage this. JSON only." \
  --max-turns 4 --output-format json

That primitive + YAML = PR reviewer, failure triage, gated deploys.
Promotion to prod always passes a human gate.

E12 · 15 min

Pipe the real log you brought. Debate: auto-act on confidence: high?

§3 · Cloud (AWS)

It's a CLI — it runs where your code runs

  • EC2 + tmux: the agent keeps working after your laptop sleeps
  • CLAUDE.md travels with the clone — remote boxes arrive pre-briefed
  • CLAUDE_CODE_USE_BEDROCK=1 — auth via your own AWS IAM
    often the difference between "security said no" and "200 engineers onboarded"
§3 · Production monitoring

Two dashboards — don't conflate them

Your team's tool

Claude Code emits OpenTelemetry natively: cost per engineer, acceptance rates

Your AI feature

cost · reliability · quality via sampled evals · safety

First alert to write: judge-score drop on sampled prod traffic — fluent-but-wrong is the failure nothing else catches.
